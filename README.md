# 서울시 실시간 인구 핫스팟

서울시 실시간 인구·혼잡도 데이터로 **"지금 갈 만한 곳"을 추천**하는 웹 앱.
사용자 선호(나이대·분위기·카테고리)에 맞춰 현재 시점의 장소를 점수화해 보여줍니다.

> 🔗 배포: [seoulpeople.vercel.app](https://seoulpeople.vercel.app)

## 왜 만들었나 (Painpoint)

> "가려는 곳이 **지금** 붐비는지 모른 채 갔다가 헛걸음한다."

맛집·관광지를 검색하면 평점·리뷰는 나오지만 **'지금 이 순간'의 혼잡도**는 알 수 없습니다.
서울시는 120개 주요 지역의 실시간 인구 데이터를 공개하지만, 원본 API는
지역명 표기가 제각각이고(`강남` vs `강남 MICE 관광특구`) 응답이 느려 그대로 쓰기 어렵습니다.

그래서 **"실시간 혼잡도 + 내 취향"을 합쳐 지금 갈 곳을 골라주는** 앱을 만들었습니다.

## 문제 → 해결 → 결과

### 문제 1. 추천을 위해 매번 주요 지역 전체를 다시 받아오면 호출이 폭증한다

추천 화면은 15개 주요 지역(강남·명동·홍대 등)의 실시간 데이터를 한꺼번에 필요로 합니다. 앱을 열 때마다 전부 재요청하면 **열 때마다 15회** 외부 API 호출이 발생합니다.
(현재 보고 있는 지역의 3분 폴링은 의도적으로 캐시를 우회해 항상 최신값을 가져옵니다 — 캐시 최적화 대상은 이 폴링이 아니라 **반복 방문 시의 주요 지역 재수집**입니다.)

- **시도 ①** 단순 캐싱 → 실시간 데이터가 금방 낡아 혼잡도가 틀어짐
- **해결** 시간대·지역 중요도별 **동적 캐시 만료** 도입
  - 출퇴근 피크(7–10시·17–20시): 주요 지역 15분 / 일반 30분
  - 비피크: 주요 지역 1시간 / 일반 3시간
  - 사전 수집 로직은 TTL 내 캐시가 있으면 재요청을 건너뜀
- **결과** 사용 패턴에 따라 외부 API 호출을 **12.5%–83.3% 절감** (실측)

  | 사용 시나리오 | 호출 절감 |
  |---|---|
  | 비피크 잦은 재방문 (10분 간격 6회) | **83.3%** |
  | 피크 시간대 (15분 TTL, 10분 간격 6회) | **50.0%** |
  | 하루 분산 사용 (8회) | **12.5%** |

  > 측정 방법: 캐시 만료 정책을 순수 모듈([`cachePolicy.js`](frontend/src/store/cachePolicy.js))로 분리하고, 결정적 시뮬레이션([`cache-benchmark.js`](frontend/scripts/cache-benchmark.js))으로 시나리오별 네트워크 호출 수를 측정. `cd frontend && node scripts/cache-benchmark.js`로 재현 가능.

### 문제 2. 조건에 맞는 추천이 0건이면 빈 화면이 뜬다

"조용한 + 20대 + 카페"처럼 조건을 좁히면 매칭 결과가 없어 화면이 비는 경우가 발생했습니다.

- **해결** 단계별 **차선책(fallback) 대체 로직**
  1. 선호 완벽 매칭 시도
  2. 실패 시 → 혼잡도 조건을 한 단계 완화(예: '약간 붐빔'까지 허용)
  3. 그래도 없으면 → 전체에서 가장 덜/더 붐비는 순으로 상위권 장소를 강제 표시(차선책은 −10점 감점 후 안내 문구 표시)
- **결과** **추천 0건 상황 제거** — 어떤 조건에서도 최소 1건 이상 노출

### 문제 3. 원본 API의 지역명이 제각각이라 검색이 안 된다

- **해결** 서버리스 함수에서 **별칭 매핑 테이블** 적용(`홍대`/`홍익대`/`홍대역` → `홍대 관광특구`) + 키워드 기반 검색
- **결과** 사용자가 일상 표현으로 검색해도 정확한 지역 데이터로 연결

### 문제 4. 네트워크가 끊기면 앱이 멈춘다

- **해결** `online`/`offline` 이벤트 감지 → 오프라인 시 자동 갱신 중단, **마지막 캐시로 동작 유지**, 복구 시 즉시 재갱신
- **결과** 지하철·실내 등 불안정 환경에서도 마지막 데이터로 사용 가능

## 핵심 수치

| 항목 | 값 | 비고 |
|---|---|---|
| 데이터 갱신 주기 | 3분 | 현재 보는 지역 폴링(강제 갱신) |
| 동적 캐시 만료 | 15분–3시간 | 시간대·지역별 차등 |
| API 호출 절감 | 12.5%–83.3% | 시뮬레이션 실측(사용 패턴별) |
| 사전 캐싱 주요 지역 | 15곳 | 강남·명동·홍대 등 |
| 추천 점수 | 기본 50 + 나이대(0–30) + 혼잡도(0–30) + 카테고리(0–30) | 차선책 −10 |
| 혼잡도 레벨 | 5단계 | 여유–매우 붐빔 |
| 초기 JS 번들 | 483.69 kB / gzip 153.17 kB | 코드 스플리팅 후 실측 (분할 전 889.96kB에서 −45.6%) |
| 지연 로딩 청크 | recharts 402.32 kB | 장소 선택 시에만 로드 |
| 빌드 산출물(CSS) | 46.38 kB / gzip 11.73 kB | 실측 |

## 기술 스택

- **Frontend**: React 19, Vite, Zustand(+persist 미들웨어), React-Leaflet(지도), Recharts(차트)
- **Backend**: Vercel Serverless Functions (`/api/population`, `/api/areas`)
- **Data**: 서울시 실시간 도시데이터 OpenAPI
- **Infra**: Vercel(주 배포) / Docker + Nginx 프록시(대체 배포)

## 아키텍처

```
[브라우저 SPA] ──/api/population──▶ [Vercel Function] ──▶ [서울시 실시간 API]
      │                                    │
      │                              지역명 매핑·정규화
      ▼
[Zustand Store + 동적 캐시 + 추천 엔진]
      │
      ├─ 동적 캐시 만료(시간대·지역별)
      ├─ 추천 점수 계산 + 차선책 fallback
      └─ 오프라인 감지 / 자동 갱신
```

## 프로젝트 구조

```
.
├── frontend/                 React + Vite SPA
│   ├── src/
│   │   ├── components/       지도·검색·추천·선호도 UI
│   │   ├── store/            Zustand 스토어 + cachePolicy.js(캐시 정책 단일 출처)
│   │   └── utils/            성능 최적화 유틸
│   └── scripts/              cache-benchmark.js (캐시 절감 측정)
├── api/                      Vercel 서버리스 함수
│   ├── population.js         실시간 인구 데이터 + 지역명 매핑
│   ├── areas.js              지역 목록 + 키워드 검색
│   └── data/                 지역 메타데이터
├── proxy/                    Nginx 프록시(Docker 대체 배포)
└── vercel.json               라우팅·CORS 설정
```

## 알려진 한계

- **호출 절감 수치**(12.5–83.3%)는 캐시 정책 시뮬레이션 기반입니다. 실제 트래픽 분포에 따라 달라질 수 있습니다.
- 데이터 출처가 서울시 실시간 도시데이터로 한정되어 타 지역은 지원하지 않습니다.
